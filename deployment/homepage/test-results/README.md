# 배포·캐시 설정 저장소 정리 검증

## 목적

VM에 적용한 배포·캐시 정리 스크립트를 저장소로 옮겨도 기존 메모리 정책과 안전 경계가 유지되는지 확인했습니다. 정책 누락 차단, 새 이미지의 설정 계승, 실패 시 복구, 생성 캐시만 정리하는 조건을 성공 기준으로 삼았습니다.

이번 검증은 저장소 정리 PR을 위한 로컬 시험입니다. 운영 VM·DB에 접속하지 않았고 인증·출석·점수 코드를 변경하거나 운영 배포하지 않았습니다.

## 테스트 방법

### 정책·캐시·systemd 설정 검사

```bash
python3 deployment/homepage/tests/run_checks.py --run-id repository-runtime-checks-01
```

정책 예시를 실제 로더로 읽고 필수값 누락·잘못된 값·후보의 잘못된 캐시 마운트를 거부하는지 검사했습니다. 캐시 정리에는 합성 캐시와 외부 링크 대상 보존용 파일을 사용했습니다. 서비스의 쓰기 경계·UID/GID·타이머 연결도 함께 대조했습니다.

### 로컬 Docker 교체·복구 검사

```bash
python3 deployment/homepage/tests/docker_deployment.py --run-id repository-docker-deploy-02
```

미리 적재한 호환 홈페이지 이미지를 사용했습니다. 새 실행은 고유한 이름과 라벨을 생성하고, 해당 실행의 시험 컨테이너·네트워크·이미지만 정리합니다. 원격 Docker 주소를 거부하고 CLI와 API가 같은 로컬 Unix 소켓을 사용하도록 고정했습니다.

1. 정책 누락을 거부하는지 확인했습니다.
2. 확인 모드가 기존 시험 프론트를 바꾸지 않는지 확인했습니다.
3. 시작하지 않는 실제 후보를 생성해 메모리·환경·캐시 설정을 검사한 뒤 제거했습니다.
4. 다른 불변 이미지로 시험 프론트를 교체하고 정책·시험 환경·리비전 라벨이 유지되는지 확인했습니다.
5. 상태 확인 실패를 유도하고 이전 시험 프론트의 이미지·이름·재시작 정책·응답이 복구되는지 확인했습니다.

[포맷 검사 기록](repository-format-checks-01.json)도 별도로 보관했습니다. 최초 제한된 네트워크에서는 pnpm registry fetch 실패로 중단됐습니다. 서명 검사를 우회하지 않고 정상 네트워크에서 포맷·검사를 완료했으며 Prettier 검사 종료 코드는 0입니다. 시작 시각·별도 실시간 로그 파일은 수집하지 않아 도구 결과 요약으로 구분했습니다.

표준 검사 11개는 다음 경계를 확인했습니다.

- 정책 예시의 유효성, 필수값 누락, 검증한 메모리 프로필의 약화 거부를 확인했습니다.
- 새 이미지에 메모리·캐시 설정을 적용하면서 인증 시험값·포트·CPU·보안 설정을 보존했습니다.
- 후보의 캐시 누락·읽기 전용 마운트·환경 누락을 거부했습니다.
- 만료 정리, 용량 정리, 최근 변경 보존, 표식 누락 거부, 심볼릭 링크 루트 거부를 확인했습니다.
- systemd 서비스와 정책의 쓰기 경계·실행 계정·타이머 연결이 일치했습니다.

로컬 Docker 9사례는 필수 설정 누락 4사례와 정상 정책 읽기, 확인 모드, 후보 검사, 새 이미지 교체, 실패 복구입니다. 새 이미지는 앱 파일을 바꾸지 않고 리비전 라벨만 바꾼 통제된 이미지입니다.

## 검증 과정에서 확인된 사항

- 첫 Docker 실행은 로컬 사전 명령에서 중단됐습니다. 당시 원문 오류와 호출 명령을 기록하지 않아 정확한 원인은 확정하지 않았습니다. 로컬 연결·이미지 가용성을 별도로 확인한 뒤 명령 종류·종료 코드·파일명·행 번호만 기록하도록 보완했고, 별도 실행02에서 전 과정을 통과했습니다.
- Docker 원시 이벤트의 `productionFrontendRestarted`는 기존 배포 스크립트가 출력한 필드명입니다. 이 시험에서는 **로컬 합성 프론트의 중지 여부**를 뜻하며 실제 운영 재시작을 의미하지 않습니다. 실행 요약의 운영 작업 수는 0건입니다.
- 운영의 전체 DB 정합성, 실제 출석 제출·상점 부여, 새로운 기능 코드의 업무 호환성, VM 재부팅, 최대 트래픽·장기 메모리 누수는 이번 시험 범위가 아닙니다.
- systemd 구성은 파일 간 일치와 보호 설정을 검사했습니다. 이번 PR에서 운영 서비스·타이머를 설치하거나 실행하지 않았습니다.
- 기본 프론트 CI에 새 운영 배포 연결을 추가하지 않았습니다. 스크립트를 설치·배포하는 작업은 별도 운영 작업입니다.
